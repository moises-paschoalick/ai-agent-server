# Agent Server Playground (frontend)

Web playground for the Agent Server sync API: chat with the agent, play the client side of a tool call (see the call and its arguments, send the result), and manage threads, tools, the system prompt and the model.

It also manages the `/v1` assistants: the **Assistant** dropdown at the top of the sidebar lists every page of `GET /v1/assistants`, newest first, with create (+), edit (✎) and delete (🗑, with confirmation). The editor (`AssistantEditor`) has every field; tools are a JSON list in the OpenAI format and metadata a JSON object, both checked before sending, and backend errors stay in the editor. Updates are partial (`POST /v1/assistants/{id}`), so `response_format`, which the editor does not show, is kept. The editor has a checkbox per system tool (`GET /tools`, `kind` `system`): checking one adds `{"type":"function","function":{"name":"..."}}` to the tools JSON; in the sidebar, declared system tools show with a lock and the server's definition. The selection lives in `hooks/useAssistants.ts` and writes nothing to the backend. With an assistant picked, the model, system instructions and tools of the sidebar are its own and save to it (`POST /v1/assistants/{id}`); "Sem assistant" shows the global settings (`/model`, `/system-prompt`, `/tools`). Threads belong to no assistant (as in OpenAI): every message goes to `POST /chat` with the picked `assistant_id`, and "new thread" only clears the chat until the first message creates it. The thread menu (`ThreadMenu`) in the chat header lists `GET /threads/summaries` grouped by the last assistant that answered (the picked one first, "Sem assistant" last), with search, new thread, history and delete; opening a thread picks that assistant, and picking an assistant opens the most recent thread it answered. Debug mode (`</>`) is at the right of the chat header; it also shows the time to the first piece of text (`ttft_ms`) and the total time of each answer. The left panel closes with the button in its header and reopens from the chat header.

Tools can be generated by the model (`POST /tools/generate`): the "Create New Tool" modal of the sidebar has a "What should the tool do?" field and **Generate**, which fills name, description and parameters (still editable) with the model of the picked assistant or the global one; the assistant editor has **Generate tool**, which shows the generated tool in the OpenAI format, editable, and **Add** appends it to the tools JSON (a repeated name or invalid JSON is refused with the reason). Nothing is saved until you save the tool or the assistant.

It came from the `front-web` folder of the earlier Python project (`ai-langchain-openrouter-agent`, commit `8928a54`) and was adapted to this backend.

## Run in development

```bash
npm install
npm run dev        # http://localhost:3000
```

The app only calls `/api/...` on its own origin. The Vite dev server proxies `/api/*` to the backend and adds the API key there:

| Variable | Default | Meaning |
| --- | --- | --- |
| `BACKEND_URL` | `http://localhost:8080` | where the backend runs |
| `AGENT_API_KEY` | (empty) | one of the backend's `AGENT_API_KEYS`; sent as `Authorization: Bearer` by the proxy only |

Both come from the environment or from the repository's root `.env`. They are not `VITE_*` variables, so Vite never puts them in the browser bundle.

## Container

`Dockerfile` builds the app and serves it with nginx (`nginx.conf.template`). nginx proxies `/api/` to `BACKEND_URL` with `AGENT_API_KEY`, and listens on `PORT` (default 80).

With `FRONTEND_USER` and `FRONTEND_PASSWORD` set, every page and `/api` need basic auth. Turn it on before exposing the frontend publicly: anyone who can open it can use the API through the proxy.

```bash
docker build -t agent-server-frontend .
docker run -p 3000:80 -e BACKEND_URL=http://host.docker.internal:8080 -e AGENT_API_KEY=... agent-server-frontend
```

From the repository root, `docker compose up --build` runs it together with the backend.

Answers are streamed by default: the chat sends `stream: true` and shows the text as it arrives, with a cursor while it is still being written (`services/sse.ts` reads the server-sent events over `fetch`, since `EventSource` cannot POST). A tool call is shown as before; an error after part of the text keeps that text and shows the error on the message. Opening another thread stops an answer still arriving, and the backend stops generating it. **Stream responses**, under the model in the sidebar, turns this off (whole answers, as before); the choice is remembered in the browser. The nginx of the image and the Vite dev server pass the events through without buffering.
